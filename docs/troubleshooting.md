# 트러블슈팅 기록

> 게임 개발 작업에서 문제를 해결할 때마다 이 파일 맨 아래에 같은 형식으로 항목을 계속 추가합니다.

슬롭메이커(slopmaker) 개발 중 겪은 기술 문제와 해결 과정을 날짜순으로 쌓는 문서입니다. 항목마다 문제 상황, 원인, 해결 과정, 배운 점을 적고, 아직 끝나지 않은 문제는 "상태: 진행 중"으로 표시합니다.

**개발 환경 요약**
- 게임: 브라우저에서 돌아가는 PC용 외주 개발사 경영 시뮬레이션 (HTML, JS, Canvas)
- 개발 방식: 클라우드 컨테이너에서 도는 AI 코딩 에이전트(Claude)에게 작업을 맡기고 결과를 검토
- 이미지 생성: 개인 PC(DESKTOP-EDP75H1, RTX 5070 Ti 16GB)에 설치한 ComfyUI

## 2026-11-07 첫 프로토타입 그래픽이 "AI가 만든 티"가 남

**문제 상황**
첫 플레이어블(아이소메트릭 사무실 씬, 자원바, 하단 도크, 인스펙터, 커스텀 커서와 클릭 이펙트)을 만들었다. 작업 전에 AI 슬롭 느낌을 줄이는 규칙(가운뎃점 금지, 설명 문장 대신 아이콘과 툴팁, Impeccable 안티패턴 목록: 순백과 순흑 대신 틴트 색, bounce 이징 금지, 카드 안 카드 금지)을 정해 적용했는데도, 화면을 보자마자 "디자인이 너무 슬롭"이라는 평가가 나왔다.

**원인**
- 모든 패널에 같은 외곽선, 오프셋 그림자, 둥근 모서리, 스트라이프 리본을 반복해서 카툰 UI 키트 템플릿처럼 보였다.
- 캐릭터와 가구를 Canvas 도형으로 직접 그려서, 얼굴 없는 덩어리 캐릭터와 휑한 플랫 아이소 사무실 수준에 머물렀다.
- 처음 진단할 때 UI 구조 문제로 해석해서 "픽셀 사무실과 서류 UI", "90년대 사무실 OS" 같은 UI 방향 선택지를 냈다. 하지만 실제 지적은 UI가 아니라 캐릭터와 가구 그림 자체였다. UI는 그림 때문에 아예 살펴보지도 못한 상태였다.

**해결 과정**
- 잘못 고른 UI 방향 결정은 취소하고, UI 구조는 그대로 둔 채 그림만 다시 하기로 범위를 좁혔다.
- 코드로 그리던 캐릭터와 가구를 이미지 생성(ComfyUI)으로 뽑은 스프라이트로 바꾸는 파이프라인으로 전환했다.
- 에셋 목록(직원 8명 2포즈, 거래처와 유튜버, AI 서버랙 5종, 가구 10종, 바닥과 벽), 공통 스타일 프롬프트, 출력 크기, 파일 이름을 담은 생성 지시문을 작성했다.
- 슬롭 제거 규칙은 프로젝트 메모리에 저장해 이후 작업에도 자동으로 적용되게 했다.

**배운 점**
- "슬롭" 느낌은 개별 요소보다 같은 처리가 모든 곳에 반복될 때 생긴다.
- 피드백이 어느 층(UI 구조인지 시각 에셋인지)을 향하는지 먼저 확인해야 한다. 범위를 잘못 잡으면 대안을 여러 개 만들어도 헛수고가 된다.
- 게임 아트 품질은 코드 드로잉으로 끌어올리기 어렵다. UI 구조와 아트는 분리해서 판단하고 만드는 편이 낫다.

## 2026-11-07 클라우드 개발 환경에서 이미지 생성 모델을 돌릴 수 없음

**문제 상황**
ComfyUI로 스프라이트를 뽑으려 했지만, AI 에이전트가 도는 클라우드 컨테이너에서는 실행할 수 없었다.

**원인**
- 컨테이너에 GPU가 없다.
- 네트워크 정책이 huggingface.co를 막아서 모델 파일도 받을 수 없다.

**해결 과정**
- 처음에는 에이전트가 사용자 PC에 ComfyUI가 있는지 확인하지 않고 "클라우드 CPU로 돌리기"라는 느리고 품질이 낮은 대안부터 제시했다. 사용자가 "다른 프로젝트에선 잘 썼다"고 지적해서 방향을 바꿨다.
- 사용자 PC(RTX 5070 Ti 16GB)에 이미 설치된 ComfyUI를 쓰기로 했다.
- 역할을 나눴다. PC는 GPU가 필요한 이미지 생성을, 클라우드는 게임 코드 통합과 배포를 맡는다.

**배운 점**
- 새 환경을 꾸리기 전에 이미 가진 자원(장비, 설치된 도구)부터 확인해야 한다.
- 무거운 연산과 가벼운 작업을 서로 다른 머신에 나누면 각 환경의 제약을 피할 수 있다.

## 2026-11-08 클라우드 작업 스레드에서 PC의 ComfyUI 폴더에 연결이 안 됨

**문제 상황**
클라우드에서 도는 에이전트가 PC의 `D:\jiwon\git\comfyui`에 접근해야 했다. 사용자는 데스크톱 앱에 이 폴더를 이미 추가해 두었는데, 에이전트 쪽 연결 요청 카드에는 상관없는 다른 저장소 폴더(OptimalShipRouting)만 시작 위치로 떴다. 이 과정에서 에이전트가
- 경로를 모르는 채로 목록에 있던 아무 폴더로 연결을 요청했고,
- 다른 PC(AICA_HRD)로 잘못 요청했으며,
- 폴더가 안 잡힌 세 번째 PC에 있을 거라고 추측했다.

연결 요청은 여러 번 거절되거나 취소됐다.

**원인**
- 데스크톱 앱에 추가한 폴더 목록과, 원격 연결로 열 수 있는 기기 폴더 목록이 따로 관리됐다. 새로 추가한 폴더가 원격 쪽 목록에 늦게 반영된 것으로 보인다. (서비스 내부 동작은 직접 확인하지 못했고, 다시 조회했을 때 목록이 바뀐 것으로 판단했다.)
- 에이전트가 목록이 왜 이상한지 확인하지 않고 우회책(아무 폴더로 시작하기)을 반복했다.
- "PC 폴더를 이 대화에서 직접 쓰는 연결"과 "PC에서 별도 세션을 띄우는 원격 실행"이라는 두 방식을 사용자와 에이전트가 서로 다르게 이해하고 있었다. 사용자 입장에서는 "내 컴퓨터에서 대화 중인데 왜 원격 접근이 필요하냐"는 의문이 당연했는데, 에이전트가 클라우드에서 돈다는 점을 처음에 설명하지 않았다.

**해결 과정**
- 사용자가 `D:\jiwon\git\comfyui`와 게임 폴더를 앱에 등록하고, 다른 세션에서 접근이 되는 것까지 확인했다.
- 기기 목록을 다시 조회하니 DESKTOP-EDP75H1에 두 폴더가 모두 원격 연결 가능한 상태로 나타났다.
- 사용자가 준 경로를 그대로 지정해 연결을 요청했고, 허용된 뒤 ComfyUI 상태 확인을 시작했다.
- 재발을 막으려고 기기 이름과 정확한 폴더 경로를 프로젝트 메모리에 기록했다. 규칙도 함께 남겼다: 경로를 모르면 추측하지 말고 묻는다, 폴더를 새로 추가한 직후에는 목록을 다시 조회한다.

**배운 점**
- 연결이 안 될 때 우회책을 반복하기보다, 두 목록이 어디서 갈라지는지 먼저 확인해야 한다.
- 모르는 값(경로, 기기)은 추측하지 말고 묻는다. 엉뚱한 곳에 권한 요청을 보내는 것 자체가 사용자 신뢰를 깎는다.
- 실행 위치(클라우드)와 사용 위치(PC)가 다른 구조는 처음에 한 번 설명해야 한다.

## 2026-11-08 ComfyUI 환경이 생성 지시문의 가정과 달랐음

**문제 상황**
생성 지시문은 흔한 SDXL 워크플로를 가정하고 썼다. SDXL 체크포인트, 네거티브 프롬프트, 배경 제거 노드(rembg, BiRefNet 등)가 있다고 본 것이다. 실제 PC 환경을 확인해 보니 달랐다.
- `models/checkpoints` 폴더가 비어 있었다.
- 모델은 FLUX.2 klein 4B(텍스트로 이미지 생성)와 Qwen-Image-Edit 2511(입력 이미지가 필요한 편집용, Lightning 4steps LoRA 포함)뿐이었다.
- 배경 제거용 커스텀 노드가 없었다.

**원인**
PC 환경을 확인하기 전에 일반적인 워크플로를 기준으로 지시문을 먼저 작성했다.

**해결 과정**
- 텍스트로 생성하는 모델은 FLUX.2 klein 4B를 쓰기로 했다 (4 steps).
- **네거티브 프롬프트 문제:** klein은 증류 모델이라 cfg 1로 돌고, cfg 1에서는 네거티브 프롬프트가 무시된다. 그래서 텍스트나 그림자 같은 금지 요소를 긍정 문장으로 바꿔 넣었다 ("flat colors, no text, single object").
- **배경 제거 문제:** 흰 단색 배경에 그림자 없이 생성하도록 프롬프트를 짜고, Python flood-fill 컷아웃 스크립트로 배경을 지워 투명 PNG를 만들었다. 사용자가 이전 프로젝트에서 쓰던 방식을 재사용했고, 새 패키지는 설치하지 않았다.
- 화풍 테스트 8장(캐릭터 4장, 책상 4장)과 배경 제거본을 장당 약 3초에 뽑았고, 컷아웃 가장자리도 깔끔했다.

**배운 점**
- 도구에 넘기는 지시문은 환경을 확인한 다음에 써야 한다.
- 같은 파라미터라도 모델마다 의미가 다르다. 증류 모델에서는 cfg와 네거티브 프롬프트가 일반 모델처럼 동작하지 않는다.
- 생성 단계에서 후처리가 쉬운 조건(단색 배경, 그림자 없음)을 만들어 두면 전용 도구 없이 단순한 스크립트로 해결할 수 있다.

## 2026-11-08 화풍 테스트에서 시점 각도가 들쭉날쭉함

**상태: 진행 중**

**문제 상황**
같은 스타일 프롬프트("isometric game asset, 3/4 top-down view facing bottom-left ...")로 캐릭터와 책상을 4장씩 뽑았다. 외곽선, 2단 셀 셰이딩, 파스텔 톤 같은 화풍은 고르게 나왔지만 각도가 제각각이었다. 캐릭터 3번은 정면을 보고, 책상 4번은 거의 위에서 내려다본 각도였다. 아이소메트릭 씬에서는 모든 에셋의 각도가 같아야 한 화면에 어색하지 않게 섞인다.

**원인**
텍스트 프롬프트만으로는 시점과 구도가 고정되지 않는다. 같은 문장이어도 시드마다 해석이 달라진다.

**해결 과정 (예정)**
- 잘 나온 그림(캐릭터 1번 또는 4번, 책상 1번 또는 2번)을 기준 이미지로 골라, 전체 세트를 뽑을 때 입력으로 넣어 각도를 고정하기로 했다.
- 앉아서 일하는 직원을 책상 그림 위에 따로 겹치면 높이와 각도가 어긋나기 쉽다. 그래서 책상과 직원을 한 장으로 뽑는 방식을 제안했고, 어떤 방식으로 갈지 결정을 기다리는 중이다.

**배운 점 (현재까지)**
- 여러 장이 한 세트로 묶여야 하는 에셋은 텍스트 프롬프트만으로는 일관성이 깨진다. 기준 이미지로 묶어야 한다.
- 전체 세트를 뽑기 전에 작은 테스트 배치로 화풍과 각도를 먼저 확인하면, 수십 장을 다시 뽑는 비용을 줄일 수 있다.
