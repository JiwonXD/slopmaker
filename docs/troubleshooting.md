# 트러블슈팅 기록

> 게임 개발 작업에서 문제를 해결할 때마다 이 파일 맨 아래에 같은 형식으로 항목을 계속 추가합니다.

슬롭메이커(slopmaker) 개발 중 겪은 기술 문제와 해결 과정을 날짜순으로 쌓는 문서입니다. 항목마다 문제 상황, 원인, 해결 과정, 배운 점을 적고, 아직 끝나지 않은 문제는 "상태: 진행 중"으로 표시합니다.

**개발 환경 요약**
- 게임: 브라우저에서 돌아가는 PC용 외주 개발사 경영 시뮬레이션 (HTML, JS, Canvas)
- 개발 방식: 클라우드 컨테이너에서 도는 AI 코딩 에이전트(Claude)에게 작업을 맡기고 결과를 검토
- 이미지 생성: 개인 PC(DESKTOP-EDP75H1, RTX 5070 Ti 16GB)에 설치한 ComfyUI

## 2026-11-07 첫 프로토타입 그래픽이 "AI가 만든 티"가 남

**문제 상황**
첫 플레이어블(아이소메트릭 사무실 씬, 자원바, 하단 도크, 인스펙터, 커스텀 커서와 클릭 이펙트)을 만들었다. 작업 전에 AI 슬롭 느낌을 줄이는 규칙(가운뎃점 금지, 설명 문장 대신 아이콘과 툴팁, Impeccable 안티패턴 목록: 순백과 순흑 대신 틴트 색, bounce 이징 금지, 카드 안 카드 금지)을 정해 적용했는데도, 화면을 보자마자 "디자인이 너무 슬롭"이라는 평가가 나왔다.

**원인**
- 모든 패널에 같은 외곽선, 오프셋 그림자, 둥근 모서리, 스트라이프 리본을 반복해서 카툰 UI 키트 템플릿처럼 보였다.
- 캐릭터와 가구를 Canvas 도형으로 직접 그려서, 얼굴 없는 덩어리 캐릭터와 휑한 플랫 아이소 사무실 수준에 머물렀다.
- 처음 진단할 때 UI 구조 문제로 해석해서 "픽셀 사무실과 서류 UI", "90년대 사무실 OS" 같은 UI 방향 선택지를 냈다. 하지만 실제 지적은 UI가 아니라 캐릭터와 가구 그림 자체였다. UI는 그림 때문에 아예 살펴보지도 못한 상태였다.

**해결 과정**
- 잘못 고른 UI 방향 결정은 취소하고, UI 구조는 그대로 둔 채 그림만 다시 하기로 범위를 좁혔다.
- 코드로 그리던 캐릭터와 가구를 이미지 생성(ComfyUI)으로 뽑은 스프라이트로 바꾸는 파이프라인으로 전환했다.
- 에셋 목록(직원 8명 2포즈, 거래처와 유튜버, AI 서버랙 5종, 가구 10종, 바닥과 벽), 공통 스타일 프롬프트, 출력 크기, 파일 이름을 담은 생성 지시문을 작성했다.
- 슬롭 제거 규칙은 프로젝트 메모리에 저장해 이후 작업에도 자동으로 적용되게 했다.

**배운 점**
- "슬롭" 느낌은 개별 요소보다 같은 처리가 모든 곳에 반복될 때 생긴다.
- 피드백이 어느 층(UI 구조인지 시각 에셋인지)을 향하는지 먼저 확인해야 한다. 범위를 잘못 잡으면 대안을 여러 개 만들어도 헛수고가 된다.
- 게임 아트 품질은 코드 드로잉으로 끌어올리기 어렵다. UI 구조와 아트는 분리해서 판단하고 만드는 편이 낫다.

## 2026-11-07 클라우드 개발 환경에서 이미지 생성 모델을 돌릴 수 없음

**문제 상황**
ComfyUI로 스프라이트를 뽑으려 했지만, AI 에이전트가 도는 클라우드 컨테이너에서는 실행할 수 없었다.

**원인**
- 컨테이너에 GPU가 없다.
- 네트워크 정책이 huggingface.co를 막아서 모델 파일도 받을 수 없다.

**해결 과정**
- 처음에는 에이전트가 사용자 PC에 ComfyUI가 있는지 확인하지 않고 "클라우드 CPU로 돌리기"라는 느리고 품질이 낮은 대안부터 제시했다. 사용자가 "다른 프로젝트에선 잘 썼다"고 지적해서 방향을 바꿨다.
- 사용자 PC(RTX 5070 Ti 16GB)에 이미 설치된 ComfyUI를 쓰기로 했다.
- 역할을 나눴다. PC는 GPU가 필요한 이미지 생성을, 클라우드는 게임 코드 통합과 배포를 맡는다.

**배운 점**
- 새 환경을 꾸리기 전에 이미 가진 자원(장비, 설치된 도구)부터 확인해야 한다.
- 무거운 연산과 가벼운 작업을 서로 다른 머신에 나누면 각 환경의 제약을 피할 수 있다.

## 2026-11-08 클라우드 작업 스레드에서 PC의 ComfyUI 폴더에 연결이 안 됨

**문제 상황**
클라우드에서 도는 에이전트가 PC의 `D:\jiwon\git\comfyui`에 접근해야 했다. 사용자는 데스크톱 앱에 이 폴더를 이미 추가해 두었는데, 에이전트 쪽 연결 요청 카드에는 상관없는 다른 저장소 폴더(OptimalShipRouting)만 시작 위치로 떴다. 이 과정에서 에이전트가
- 경로를 모르는 채로 목록에 있던 아무 폴더로 연결을 요청했고,
- 다른 PC(AICA_HRD)로 잘못 요청했으며,
- 폴더가 안 잡힌 세 번째 PC에 있을 거라고 추측했다.

연결 요청은 여러 번 거절되거나 취소됐다.

**원인**
- 데스크톱 앱에 추가한 폴더 목록과, 원격 연결로 열 수 있는 기기 폴더 목록이 따로 관리됐다. 새로 추가한 폴더가 원격 쪽 목록에 늦게 반영된 것으로 보인다. (서비스 내부 동작은 직접 확인하지 못했고, 다시 조회했을 때 목록이 바뀐 것으로 판단했다.)
- 에이전트가 목록이 왜 이상한지 확인하지 않고 우회책(아무 폴더로 시작하기)을 반복했다.
- "PC 폴더를 이 대화에서 직접 쓰는 연결"과 "PC에서 별도 세션을 띄우는 원격 실행"이라는 두 방식을 사용자와 에이전트가 서로 다르게 이해하고 있었다. 사용자 입장에서는 "내 컴퓨터에서 대화 중인데 왜 원격 접근이 필요하냐"는 의문이 당연했는데, 에이전트가 클라우드에서 돈다는 점을 처음에 설명하지 않았다.

**해결 과정**
- 사용자가 `D:\jiwon\git\comfyui`와 게임 폴더를 앱에 등록하고, 다른 세션에서 접근이 되는 것까지 확인했다.
- 기기 목록을 다시 조회하니 DESKTOP-EDP75H1에 두 폴더가 모두 원격 연결 가능한 상태로 나타났다.
- 사용자가 준 경로를 그대로 지정해 연결을 요청했고, 허용된 뒤 ComfyUI 상태 확인을 시작했다.
- 재발을 막으려고 기기 이름과 정확한 폴더 경로를 프로젝트 메모리에 기록했다. 규칙도 함께 남겼다: 경로를 모르면 추측하지 말고 묻는다, 폴더를 새로 추가한 직후에는 목록을 다시 조회한다.

**배운 점**
- 연결이 안 될 때 우회책을 반복하기보다, 두 목록이 어디서 갈라지는지 먼저 확인해야 한다.
- 모르는 값(경로, 기기)은 추측하지 말고 묻는다. 엉뚱한 곳에 권한 요청을 보내는 것 자체가 사용자 신뢰를 깎는다.
- 실행 위치(클라우드)와 사용 위치(PC)가 다른 구조는 처음에 한 번 설명해야 한다.

## 2026-11-08 ComfyUI 환경이 생성 지시문의 가정과 달랐음

**문제 상황**
생성 지시문은 흔한 SDXL 워크플로를 가정하고 썼다. SDXL 체크포인트, 네거티브 프롬프트, 배경 제거 노드(rembg, BiRefNet 등)가 있다고 본 것이다. 실제 PC 환경을 확인해 보니 달랐다.
- `models/checkpoints` 폴더가 비어 있었다.
- 모델은 FLUX.2 klein 4B(텍스트로 이미지 생성)와 Qwen-Image-Edit 2511(입력 이미지가 필요한 편집용, Lightning 4steps LoRA 포함)뿐이었다.
- 배경 제거용 커스텀 노드가 없었다.

**원인**
PC 환경을 확인하기 전에 일반적인 워크플로를 기준으로 지시문을 먼저 작성했다.

**해결 과정**
- 텍스트로 생성하는 모델은 FLUX.2 klein 4B를 쓰기로 했다 (4 steps).
- **네거티브 프롬프트 문제:** klein은 증류 모델이라 cfg 1로 돌고, cfg 1에서는 네거티브 프롬프트가 무시된다. 그래서 텍스트나 그림자 같은 금지 요소를 긍정 문장으로 바꿔 넣었다 ("flat colors, no text, single object").
- **배경 제거 문제:** 흰 단색 배경에 그림자 없이 생성하도록 프롬프트를 짜고, Python flood-fill 컷아웃 스크립트로 배경을 지워 투명 PNG를 만들었다. 사용자가 이전 프로젝트에서 쓰던 방식을 재사용했고, 새 패키지는 설치하지 않았다.
- 화풍 테스트 8장(캐릭터 4장, 책상 4장)과 배경 제거본을 장당 약 3초에 뽑았고, 컷아웃 가장자리도 깔끔했다.

**배운 점**
- 도구에 넘기는 지시문은 환경을 확인한 다음에 써야 한다.
- 같은 파라미터라도 모델마다 의미가 다르다. 증류 모델에서는 cfg와 네거티브 프롬프트가 일반 모델처럼 동작하지 않는다.
- 생성 단계에서 후처리가 쉬운 조건(단색 배경, 그림자 없음)을 만들어 두면 전용 도구 없이 단순한 스크립트로 해결할 수 있다.

## 2026-11-08 화풍 테스트에서 시점 각도가 들쭉날쭉함

**상태: 캐릭터는 해결, 가구는 다음 항목에서 다른 방법으로 해결**

**문제 상황**
같은 스타일 프롬프트("isometric game asset, 3/4 top-down view facing bottom-left ...")로 캐릭터와 책상을 4장씩 뽑았다. 외곽선, 2단 셀 셰이딩, 파스텔 톤 같은 화풍은 고르게 나왔지만 각도가 제각각이었다. 캐릭터 3번은 정면을 보고, 책상 4번은 거의 위에서 내려다본 각도였다. 아이소메트릭 씬에서는 모든 에셋의 각도가 같아야 한 화면에 어색하지 않게 섞인다.

**원인**
텍스트 프롬프트만으로는 시점과 구도가 고정되지 않는다. 같은 문장이어도 시드마다 해석이 달라진다.

**해결 과정**
- 사용자가 테스트 결과 중 캐릭터 1번과 책상 2번을 기준 이미지로 골랐다.
- 캐릭터는 기준 이미지를 Qwen-Image-Edit에 넣고 외모나 포즈만 바꾸는 방식으로 뽑았다. 직원 8명 x 포즈 10종을 같은 각도와 등신으로 맞출 수 있었다.
- 모든 스프라이트를 1024 캔버스에 같은 기준점(머리 중심 x 512, 발바닥 y 1000)으로 맞추고 anchors.json에 기록했다. 좌우 반전만으로 반대 방향을 만들 수 있어서 뒷모습은 따로 뽑지 않기로 했다.
- 가구는 기준 이미지를 넣어도 각도가 맞지 않는 경우가 남았다. 이건 아래 "가구 각도와 배치가 어긋남" 항목에서 다른 방법으로 해결했다.

**배운 점**
- 여러 장이 한 세트로 묶여야 하는 에셋은 텍스트 프롬프트만으로는 일관성이 깨진다. 기준 이미지로 묶어야 한다.
- 전체 세트를 뽑기 전에 작은 테스트 배치로 화풍과 각도를 먼저 확인하면, 수십 장을 다시 뽑는 비용을 줄일 수 있다.
- 기준점(앵커)을 처음부터 숫자로 정해 두면 게임에서 겹치기, 반전, 축소가 단순해진다.

## 2026-11-08 캐릭터를 통짜로 뽑을지 부품으로 나눌지, 그리고 걷기 동작의 한계

**문제 상황**
처음에는 앉아서 일하는 직원을 책상과 한 장으로 뽑자고 제안했다. 사용자가 "캐릭터, 가구는 따로 컴포넌트로 뽑고 레이어로 쌓아서 관리해야 하는 것 아니냐"고 지적했다. 또 사무실이 살아 보이도록 직원이 정수기, 커피, 화장실에 다녀오고, 서성이고, 동료 자리에 가서 대화하는 동작이 필요했다.

**원인**
통짜 그림을 제안한 이유는 AI로 따로 뽑으면 각도와 크기가 어긋나기 쉬워서였다. 하지만 그 문제는 기준 이미지와 기준점으로 해결할 수 있었고, 통짜 그림은 재사용과 애니메이션이 어렵다.

**해결 과정**
- 가구(책상, 의자, 소품)와 캐릭터를 따로 뽑고, 화면 깊이 순서(의자, 캐릭터, 책상)로 겹쳐 그리는 레이어 방식으로 바꿨다.
- 캐릭터 1명으로 파일럿을 먼저 했다. 포즈 12장과 가구 5종을 뽑아 겹치기 테스트를 한 뒤 승인받고 나머지 7명으로 늘렸다.
- 걷기는 Qwen-Image-Edit에 "오른쪽 다리 앞, 왼쪽 다리 뒤"처럼 신체 기준으로 지시하고 시드를 바꿔 여러 번 시도했지만, 다리가 좌우로 교차하는 프레임이 끝내 나오지 않았다. 억지로 4프레임을 맞추지 않고 2프레임 반복으로 확정했다. 이동, 몸 흔들림, 숨쉬기는 코드로 움직였다.
- 게임용으로는 원본 1024px PNG를 1/4 크기(256px) webp로 줄이고, 기준점과 크기를 manifest.json 하나로 모았다. 결과는 webp 98개, 총 약 1MB다.

**배운 점**
- "AI가 잘 못 맞추니까 합쳐서 뽑자"는 생성 도구의 한계에 구조를 맞추는 선택이다. 한계를 다른 방법(기준 이미지, 기준점)으로 메울 수 있으면 표준 구조를 지키는 편이 낫다.

## 2026-11-08 가구 각도와 배치가 어긋남

**문제 상황**
생성한 가구를 게임에 넣었더니 사용자가 "가구들 직각도 안 맞고 위치도 이상하다"고 지적했다. 나중에는 책장이 창문을 가리는 배치도 지적받았다.

**원인**
가구 그림과 바닥 격자의 각도를 실제로 재 보니 세 가지가 겹쳐 있었다.
- 생성된 가구마다 각도가 달랐다. 박스와 서버랙은 30도 아이소였지만, 책상과 회의 테이블은 한쪽 모서리만 맞았고, 프린터, 책장, 화이트보드는 거의 정면에서 본 각도였다.
- 게임 바닥 격자는 26.6도(가로세로 2:1 마름모)라서, 30도로 맞게 나온 가구조차 바닥과 살짝 어긋났다.
- 가구를 격자 칸에 맞추지 않고 좌표를 대충 찍었고, 빈자리를 소파나 테이블로 아무렇게나 채웠다.

**해결 과정**
- 바닥을 정확한 30도 아이소(트루 아이소)로 바꿨다.
- 가구마다 크기(가로 칸, 세로 칸, 높이 칸)를 정하고, Python으로 그 크기의 30도 상자 윤곽 가이드 이미지를 그렸다. 정면, 옆면, 윗면을 다른 회색으로 칠해 방향이 보이게 했다.
- 이 가이드 한 장을 Qwen-Image-Edit에 넣고 "이 상자 윤곽에 정확히 맞춰 가구를 그려라"고 지시해 시드 여러 개로 생성했다.
- 자동 검수를 붙였다. 배경을 지운 가구 실루엣과 가이드 상자 실루엣의 IoU(겹치는 비율)를 계산해서 0.85 미만은 버리고, 통과한 것 중 가장 높은 것을 골랐다.
- 이 방식으로 가구 10종과 AI 서버랙 5종을 다시 뽑았고, 모두 바닥 격자와 같은 각도로 칸에 맞춰 배치했다. 의자와 화분은 둥근 물건이라 기존 그림을 그대로 썼다.
- 배치는 칸 단위로 다시 짰다. 업무석은 2칸 책상 줄, 휴게(정수기, 커피, 화장실)는 왼쪽 벽, 서버는 오른쪽, 소파와 회의 테이블은 아래쪽에 모았다.
- 창문 문제는 순서를 바꿔 해결했다. 가구를 먼저 놓고, 창턱보다 높은 가구(책장, 화이트보드)가 없는 벽 구간에만 창문을 낸다. 사무실이 넓어져도 같은 규칙이 적용된다.

**배운 점**
- "이상해 보인다"는 피드백은 감으로 고치지 말고 각도처럼 잴 수 있는 값으로 바꿔서 원인을 찾아야 한다.
- 생성 모델에게 "아이소메트릭"이라는 단어 대신 정확한 기하 가이드를 주면 각도를 강하게 통제할 수 있다.
- 생성 결과를 사람이 일일이 고르지 않고 IoU 같은 수치로 자동 검수하면, 일관성을 유지하면서 많은 에셋을 빠르게 걸러낼 수 있다.
- 배치 규칙(창문은 높은 가구가 없는 곳에만)을 코드로 정해 두면 맵이 커져도 같은 실수를 반복하지 않는다.

## 2026-11-08 직원 외모를 다양하게 만드는 방식 선택

**문제 상황**
직원 8명만으로는 고용할 때마다 같은 얼굴이 반복된다. 사용자가 "마네킹 같은 사람 형체를 먼저 뽑고 옷, 머리, 액세서리를 조합해서 만드는 게 어떠냐"고 제안했다.

**원인 (완전 조립식의 위험)**
- 옷과 머리를 따로 생성하면 포즈 10개마다 픽셀 단위로 정확히 겹쳐야 한다. 생성 모델은 이걸 맞추지 못해서 소매와 팔, 머리와 얼굴 경계가 어긋나고, 레이어마다 외곽선 굵기와 음영도 달라진다.
- 타이핑이나 컵 들기처럼 팔이 옷 앞으로 오는 포즈는 포즈마다 레이어 순서가 바뀌어 조립이 더 복잡해진다.

**해결 과정**
- 절충안을 제안했고 사용자가 골랐다. 기존 8명 그림을 바탕으로 쓰고, 그림을 피부, 머리카락, 상의, 하의, 신발 영역으로 나눈 마스크를 만들었다. 게임 코드에서 영역별로 색을 바꿔 칠한다.
- 마스크는 캐릭터별 색 설정과 위치(머리는 위, 신발은 맨 아래)로 픽셀을 분류해 만들었다. 셀 셰이딩의 어두운 단계도 같은 영역으로 묶었고, 외곽선은 원래 색으로 남겼다. 그래서 색을 바꿔도 명암이 그대로 살아 있다.
- 안경 2종, 헤드폰, 모자, 비니 같은 작은 액세서리만 따로 뽑았다. 포즈마다 머리 중심과 폭을 기록해 두고 그 위치에 얹었다.
- 결과적으로 8명 x 색 조합 x 액세서리로 외모가 다양해졌고, 그림 품질은 그대로 유지됐다.

**남은 문제**
기지개 포즈처럼 고개가 기울면 안경이 살짝 어긋난다. 체크 셔츠 직원은 두 포즈에서 소매 일부가 원래 색으로 남는다.

**배운 점**
- 일반 게임 제작의 정석(부위별 레이어 조립)이 생성 이미지에서는 그대로 통하지 않을 수 있다. 도구의 강점(한 장 안의 일관성)을 살리는 쪽으로 구조를 바꾸면 같은 목표를 더 적은 위험으로 얻을 수 있다.
- 제안을 그대로 받거나 거절하는 대신, 위험을 설명하고 절충안을 선택지로 내면 결정이 빨라진다.

## 2026-11-08 원본 PNG까지 저장소에 잘못 올라감

**상태: 미해결 (저장소 기록에 원본이 남아 있음)**

**문제 상황**
게임에 필요한 건 1/4 크기 webp 세트(약 1MB)뿐이었는데, PC에서 첫 커밋을 push할 때 원본 PNG까지 같이 올라갔다. 338개 파일, 약 100MB였다.

**원인**
원본 폴더를 커밋에서 빼라고 지시했지만, push 전에 실제 커밋에 들어간 파일 목록과 크기를 확인하지 않았다.

**해결 과정**
- 게임용 세트만 담은 커밋을 다시 만들었다. 잘못 올린 커밋을 덮어쓰는 force push가 필요해서, 덮어쓸지 사용자에게 결정 카드로 먼저 물었고 승인을 받았다.
- 덮어쓰기는 `git push --force-with-lease=main:9b008a5` 로, 원격이 예상한 커밋일 때만 덮어쓰게 했다.
- 그런데 PC 쪽 Claude Code 권한 설정이 force push를 막았다. 사용자에게 터미널에서 직접 실행해 달라고 안내했지만 실행되지 않은 채로 다른 작업이 이어졌다.
- 그 사이 main 위에 웹 빌드 커밋이 새로 올라가서, 지금은 원본 PNG가 든 커밋이 기록에 그대로 남아 있다. 저장소를 받으면 약 90MB를 내려받는다.

**배운 점**
- push 전에 `git status` 와 커밋에 들어간 파일 목록, 크기를 확인하는 단계를 빼먹으면 안 된다. 바이너리는 한 번 올라가면 기록에서 지우기가 훨씬 번거롭다.
- 덮어쓰기는 `--force-with-lease` 처럼 다른 사람의 커밋을 지우지 않는 안전장치를 붙여야 한다.
- 되돌리기 작업이 사용자 손을 기다리는 동안 다른 커밋을 쌓으면 정리가 더 어려워진다. 정리 작업을 먼저 끝내거나, 미뤄진다는 사실을 기록해 둬야 한다.

## 2026-11-08 Vercel 배포를 로컬 명령에서 GitHub 연동 자동 배포로 전환

**문제 상황**
Vercel로 배포하기로 한 뒤, 에이전트는 사용자에게 PC 터미널에서 `npx vercel login` 과 `npx vercel --prod` 를 직접 실행하라고 안내했다. 사용자는 "Vercel은 클라우드에서 돌아가는데 왜 로컬에서 명령어를 치게 만드냐"고 지적했다. 같은 시간대에 사용자가 Vercel로 운영 중이던 다른 서비스(certifiquiz)가 먹통이 되어, 이번 작업이 원인인지 확인해야 했다.

**원인**
- Vercel이 파일을 받는 길은 두 가지다. 파일이 있는 컴퓨터에서 CLI로 올리거나, Vercel이 GitHub 저장소에서 직접 가져가는 것이다.
- 에이전트가 도는 클라우드 환경은 네트워크에서 Vercel 접속이 막혀 있었고, Claude GitHub 앱이 저장소에 설치되지 않아 GitHub push도 막혀 있었다. 그래서 가장 쉬운 우회로인 "사용자 PC에서 CLI 실행"을 안내했다. 하지만 이건 반복 작업을 사용자에게 떠넘기는 방식이었다.

**해결 과정**
- certifiquiz 건은 먼저 읽기 전용으로 조사했다. 클라우드와 PC 양쪽 기록, PowerShell 기록에 vercel이나 npx 실행이 한 번도 없었고, PC에 Vercel 로그인 정보와 `.vercel` 연결 폴더도 없었다. 이번 작업이 certifiquiz를 건드릴 수 없는 상태였음을 근거와 함께 보고하고, Vercel 대시보드에서 확인할 항목(최신 배포 상태, 오류 로그, 사용량)을 안내했다.
- 배포 방식은 GitHub 연동으로 바꿨다. 사용자가 할 일은 Claude GitHub 앱을 저장소에 설치하고 Vercel에서 저장소를 Import 하는 두 번의 클릭뿐이다.
- 사용자가 두 가지를 마친 뒤, 에이전트가 클라우드에서 저장소에 게임 파일(web/index.html, vercel.json)을 직접 push했다. 이제 push할 때마다 Vercel이 자동으로 배포하는 구조다. (이 항목을 쓴 시점에는 첫 자동 배포 주소가 열리는지 아직 확인하지 못했다.)

**배운 점**
- 배포 파이프라인은 한 번 연결해 두고 이후 반복을 자동화하는 쪽으로 설계해야 한다. "지금 당장 되는 우회로"가 매번 사람 손을 요구하면 좋은 해결이 아니다.
- 다른 서비스 장애처럼 의심받는 상황에서는 추측으로 부정하지 말고, 실행 기록과 설정 파일 같은 증거로 무관함을 확인해서 보고한다. 조사는 아무것도 바꾸지 않는 읽기 전용으로 한다.

## 2026-11-09 저작권 걱정 없이 BGM과 효과음 넣기

**문제 상황**
게임에 배경음악과 효과음을 넣기로 했다. 외부 음원 파일은 라이선스 확인이 번거롭고, 이미 1.8MB인 단일 HTML 빌드본을 더 키운다. 여기에 브라우저 오디오에는 몇 가지 함정이 있었다.
- 브라우저 자동재생 정책 때문에 사용자 입력 전에는 소리를 낼 수 없다. 타이틀 화면에서 바로 음악을 틀면 AudioContext가 suspended 상태로 멈춰 있다.
- 저장소에는 에셋이 data URI로 박힌 빌드본(web/index.html)만 있고, 원본 소스는 따로 있다. 빌드본만 고치면 다음 빌드 때 변경이 사라진다.

**원인**
- 자동재생 차단은 오류가 아니라 정책이다. 사용자 제스처 안에서 AudioContext를 만들거나 resume 해야 한다.
- setTimeout으로 음을 하나씩 재생하면 메인 스레드가 바쁠 때(캔버스 렌더링, UI 갱신) 박자가 흔들린다. 또 탭이 숨겨지면 브라우저가 타이머를 1초 간격으로 늦춰서 음이 한꺼번에 몰리거나 끊긴다.
- 한 주가 지날 때 토스트가 여러 개 동시에 뜨면 같은 효과음이 겹쳐 터진다.

**해결 과정**
- 음원 파일 없이 Web Audio API의 오실레이터와 노이즈 버퍼로 모든 소리를 합성했다. BGM은 F장조 8마디 코드 진행 위에 베이스, 오프비트 화음, 하이햇, 고정 시드로 만든 멜로디를 얹은 칩튠 루프다. 용량 증가는 코드 약 8KB뿐이다.
- 첫 pointerdown, keydown을 캡처 단계에서 받아 AudioContext를 만든다. 캡처 단계라서 그 첫 클릭의 효과음도 바로 난다.
- 재생은 "미리 예약" 방식 스케줄러로 바꿨다. 30ms마다 깨어나서 0.15초 앞까지의 음을 오디오 클럭(ac.currentTime) 기준으로 예약하므로, 메인 스레드가 잠깐 막혀도 박자가 유지된다. 탭이 숨겨지면 AudioContext를 suspend 하고, 돌아오면 예약 시점을 현재 시각으로 당겨서 밀린 음이 몰려 나오지 않게 했다.
- 같은 효과음은 70ms 안에 다시 울리지 않게 막았다.
- 일시정지(속도 0)일 때는 BGM에 로우패스 필터를 걸어 먹먹하게 만들어, 게임이 멈췄다는 걸 소리로도 알 수 있게 했다.
- 음소거는 배경음악, 효과음을 따로 끄는 아이콘 버튼 2개(툴팁, 단축키 M, N)로 만들고 localStorage에 저장했다.
- 빌드본 반영은 "빌드본의 에셋 주입부는 그대로 두고 소스 부분만 교체"하는 스크립트로 했다. 먼저 원래 소스로 같은 과정을 돌려 기존 빌드본과 바이트 단위로 똑같이 나오는지 확인한 뒤 새 소스를 넣었다.
- Playwright로 오실레이터 생성 횟수를 세는 계측 코드를 넣어, 첫 클릭 전에는 AudioContext가 없고, 클릭 후 BGM이 돌고, 음소거하면 새 음 생성이 0이 되는 것을 확인했다.

**배운 점**
- 브라우저 오디오는 "언제 시작할 수 있나(자동재생 정책)"와 "언제 울리나(타이밍)"가 핵심이다. 박자가 중요한 소리는 JS 타이머가 아니라 오디오 하드웨어 클럭에 예약해야 한다.
- 소리처럼 귀로만 확인되는 기능도 노드 생성 횟수 같은 숫자로 바꾸면 자동으로 검증할 수 있다.
- 빌드 산출물만 저장소에 있는 구조에서는 산출물을 직접 고치지 말고 원본을 고친 뒤 같은 빌드 과정을 재현해야 한다. 재현이 맞는지는 원래 입력으로 원래 출력이 나오는지부터 확인한다.
